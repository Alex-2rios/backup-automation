# The 3-2-1 rule, and what the scripts do about it

Three copies of the data, on two different kinds of media, one of them offsite. It is the oldest
advice in backups and most home setups still fail it, usually at the same two points.

## Where the three copies live

| Copy | Setting | What it survives |
|---|---|---|
| the original | `SOURCES` | nothing, this is the thing you are protecting |
| local archive | `PRIMARY_DIR` | a deleted file, a bad edit, a failed upgrade |
| second medium | `SECONDARY_DIR` | the primary disk dying |
| offsite | `REMOTE_TARGET` | fire, theft, ransomware that reaches the whole LAN |

The two most common failures are a "second copy" that lives on the same physical disk, and an
offsite copy that quietly stopped syncing months ago. Both look fine until you need them.

`backup.sh` treats an unmounted `SECONDARY_DIR` as a failure and exits non zero, rather than
writing the archive once and reporting success. A backup job that returns 0 when it only made one
copy is worse than no job at all, because now you trust it.

## Rotation

Grandfather, father, son. Each run is tagged when it is created:

| Tier | Created on | Kept |
|---|---|---|
| monthly | the 1st | `KEEP_MONTHLY`, 6 by default |
| weekly | Sundays | `KEEP_WEEKLY`, 4 by default |
| daily | everything else | `KEEP_DAILY`, 7 by default |

With the defaults that is about 17 archives covering roughly six months: the last week day by
day, the last month week by week, and half a year month by month. Pruning happens per tier, so
a burst of daily runs can never evict your monthly copies.

The tier is baked into the filename, which is what makes the pruning simple:

```
homelab-home_arc_projects-20260818-023014-daily.tar.gz
homelab-home_arc_projects-20260818-023014-daily.tar.gz.sha256
```

## Verification

An unverified backup is a guess. Three levels, cheapest first:

1. **Checksum.** A `.sha256` is written next to every archive at creation and re-checked after
   the copy to the second medium, so a corrupt copy is caught while the good one still exists.
2. **Structure.** `tar -tf` reads the archive index. Catches truncation, which a checksum written
   after the truncation would not.
3. **Restore drill.** `verify.sh --drill` extracts the newest archive into a temporary directory
   and confirms files actually come out. This is the only one that tests the thing you care about.

```bash
./bin/verify.sh --drill
```

The weekly systemd timer runs exactly that.

## Recovery, when you actually need it

```bash
./bin/restore.sh --list
./bin/restore.sh --archive /srv/backups/homelab-etc-20260801-023000-monthly.tar.gz --to /tmp/check
```

`restore.sh` verifies the checksum before extracting and refuses to write into a directory that
is not empty. Restoring on top of live data, in a hurry, at the worst possible moment is a very
easy way to turn one problem into two.

## Scheduling

systemd timers rather than cron, for three reasons: `Persistent=true` catches up a run that was
missed because the machine was off, `RandomizedDelaySec` stops several machines hammering the
same offsite target at 02:30 exactly, and `systemctl status backup.service` shows the last run
and its output without hunting through a log.

```bash
sudo cp bin/*.sh /usr/local/bin/
sudo mkdir -p /etc/backup && sudo cp etc/backup.conf.example /etc/backup/backup.conf
sudo cp systemd/* /etc/systemd/system/
sudo systemctl daemon-reload
sudo systemctl enable --now backup.timer backup-verify.timer
systemctl list-timers 'backup*'
```

The service unit runs with `ProtectSystem=strict` and an explicit `ReadWritePaths`, so the backup
job can only write to the backup directories and the log. A job that runs as root every night is
worth confining.

## What this does not protect against

Ransomware that encrypts the primary source will happily be backed up, and if it also reaches
the mounted `SECONDARY_DIR` it takes that with it. The offsite copy over SSH is what saves you,
and only if the remote account cannot delete or overwrite what it already has. Append only
storage or snapshots on the far end are the next thing on my list.
